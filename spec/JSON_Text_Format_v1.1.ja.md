# カーリングストーン配置 JSON Text Format v1.1 一般仕様書

[English](JSON_Text_Format_v1.1.md)

英語版をcanonical specification（正本）、日本語版をofficial translation（公式翻訳）とします。

- 現行仕様バージョン: **v1.1**
- 基礎バージョン: **v1.0**

## 1. 目的

この一般仕様書は、アプリケーションやツール間でカーリングストーン配置を交換するためのJSON Text Formatを定義します。

JSONデータの構造と、アプリケーション固有の表示上の整形形式は別のものとして扱います。空白、改行、インデントはJSONデータの意味を変えず、互換性の必須条件ではありません。

## 2. バージョン判別

現時点では、JSON内部に専用のversionフィールドを設けません。

| 条件 | バージョン |
| --- | --- |
| トップレベルに `houseRadius` がない | v1.0 |
| トップレベルに `houseRadius` がある | v1.1 |

v1.0とv1.1の構造上の違いは、`houseRadius` の有無だけです。

将来さらにフォーマットを拡張する場合は、必要に応じて別のバージョニング方式を検討します。この仕様では、それ以上のバージョニング規則を定めません。

## 3. v1.0の構造

### 3.1 トップレベルフィールド

| Field | Type | 日本語での説明 |
| --- | --- | --- |
| `metadata` | 任意のJSON値 | JSON textを生成したアプリケーションやツールの名前など、説明用の情報を記載する。 |
| `positiveDirection` | string | 座標系の正方向を表す。許容値は4種類。 |
| `houseCenter` | object | ハウス中心の座標。 |
| `stones` | array | ストーン配置の配列。ストーンがない場合は空配列。 |

### 3.2 `positiveDirection`

本フォーマットの座標系は一方のハウスを基準として定義しますが、表現可能なストーン位置をそのハウス周辺に限定するものではありません。以下の向きの定義は、バックラインからホッグラインまでを有効座標範囲とするものではありません。シート上の他の場所も同じ座標系で表現でき、各実装が対応する配置範囲とは別の事項です。

バックラインがハウスの上側、ホッグラインが下側となる向きを基準として、`Up`（上）、`Down`（下）、`Left`（左）、`Right`（右）を定義しています。

次の4値は、この基準に基づくx軸とy軸の正方向を表します。

| 値 | x軸の正方向 | y軸の正方向 |
| --- | --- | --- |
| `LeftDown` | Left（左） | Down（下） |
| `LeftUp` | Left（左） | Up（上） |
| `RightDown` | Right（右） | Down（下） |
| `RightUp` | Right（右） | Up（上） |

この基準は、アプリケーションの現在の画面の向きには依存しません。

### 3.3 `houseCenter`

| Field | Type | 日本語での説明 |
| --- | --- | --- |
| `x` | number | ハウス中心のX座標。 |
| `y` | number | ハウス中心のY座標。 |

### 3.4 `stones`

`stones` の各要素は次のフィールドを含みます。

| Field | Type | 日本語での説明 |
| --- | --- | --- |
| `color` | string | ストーンの色として `"red"` または `"yellow"` を記載する。 |
| `position` | object | ストーン位置を表す座標。 |
| `number` | number | ハウス中心からの距離が近い順に各ストーンへ割り当てる、重複しない番号。 |

有効な配置に含まれるストーンは各色最大8個です。この上限を超える入力に対するReaderの回復動作（入力全体を拒否する、余分なストーンを無視するなど）は実装依存とし、本仕様では規定しません。

`number`は、色にかかわらず同じ配置内の全ストーン間で重複しないものとします。ハウス中心に近いストーンほど小さい番号を割り当てます。2個以上のストーンがハウス中心から同じ距離にある場合、それらの相対的な番号順は実装依存ですが、互いに異なる番号を割り当てる必要があります。不正なnumberやnumber重複に対するReaderの処理は実装依存とし、本仕様では規定しません。

番号の規則は、`stones`配列そのものを`number`順に並べることを要求しません。

`position` オブジェクトは次のフィールドを含みます。

| Field | Type | 日本語での説明 |
| --- | --- | --- |
| `x` | number | ストーン位置のX座標。 |
| `y` | number | ストーン位置のY座標。 |

v1.0では、`position.x` と `position.y` は実際のカーリングスケールをメートル単位で表し、小数点第3位まで記載します。

これは最大小数桁数・丸め精度の規定であり、固定小数点表記を要求するものではありません。末尾の0を付ける必要はありません。

## 4. v1.1での拡張

v1.1では、v1.0の構造へトップレベルフィールド `houseRadius` を追加します。それ以外の構造は変更しません。

### 4.1 `houseRadius.value`：スケール基準

`houseRadius.value` は、そのJSON座標系で12-foot circleの半径をいくつとして表すかを示します。`houseCenter` および `stones[].position.x/y` を含む座標系全体のスケール基準です。実寸座標、画像ピクセル座標、ゲーム・仮想空間の内部座標、縮尺モデルの座標にも共通して使用できます。

| Field | Type | 日本語での説明 |
| --- | --- | --- |
| `value` | number | 座標変換に利用可能な有限の正の数。12-foot circleの半径を表すスケール基準。 |
| `unit` | string | 単位または座標系を説明する任意の非空文字列。 |

0、負数、非有限値、および有効な数値として扱えない値はスケール基準として許容しません。

座標系宣言の例:

```json
"houseRadius":{"value":1.829,"unit":"m"}
```

```json
"houseRadius":{"value":6,"unit":"ft"}
```

```json
"houseRadius":{"value":300,"unit":"px"}
```

```json
"houseRadius":{"value":100,"unit":"game-unit"}
```

これらはv1.1一般仕様として有効な座標系表現です。特定のReaderが対応しているかどうかは別の問題です。

### 4.2 `houseRadius.unit`：ラベルと推奨表記

`unit` はvalueおよび座標が使用する単位・座標系のラベルです。列挙値には限定しません。以下は代表的な推奨表記であり、許容値の一覧ではありません。

| Label | 日本語での意味 |
| --- | --- |
| `"m"` | メートル |
| `"ft"` | フィート |
| `"px"` | ピクセル |

半径比による座標正規化には、Readerがラベルの意味を理解することを必須としません。未知のunitだけを理由として、その他の点で有効なデータ全体を拒否しないことを推奨します。共通仕様は大文字・小文字や同義語の同一視を要求しません。`"m"`、`"M"`、`"meter"`等を同一ラベルと解釈する義務はありません。

### 4.3 半径比による正規化

入力半径を `R_input`、変換先半径を `R_target` とすると、原点・方向を揃えた座標系間のスケール変換は次のように表せます。

```text
scaleFactor = R_target / R_input
targetPosition = inputPosition × scaleFactor
```

絶対座標を変換する場合はhouseCenterにも同じ係数を適用します。先に入力houseCenterを引き、相対座標へ係数を掛ける方法も同等です。原点補正とpositiveDirectionの処理は、スケール変換とは区別します。

変換先半径が1.829なら、入力半径300には `1.829 / 300`、入力半径6には `1.829 / 6` を使います。この数値変換はunit文字列の解釈を必要としません。これは座標スケールの正規化であり、物理的なフィート・メートル換算を要求するものではありません。

### 4.4 推奨座標分解能

座標値は、12-foot circleの実寸半径を1.829 mとした場合に、実寸換算で約1 mmまたはそれより細かい座標分解能を維持することを推奨します。

1 mm相当の座標刻みの目安は次の式です。

```text
recommendedResolution = houseRadius.value / 1829
```

| `houseRadius.value` | 約1 mm相当の刻み |
| --- | ---: |
| 1.829 | 0.001 |
| 6 | 0.00328 |
| 300 | 0.164 |

これは相互運用のための推奨であり、Writerへの厳密な量子化・丸め規則ではありません。より細かい分解能を保持して構いません。v1.1ではhouseRadius.valueや座標に、unit別の固定小数桁数、固定有効数字、不要な末尾ゼロを要求しません。スケール基準となる半径値も必要な精度を保持します。第3.4節のv1.0精度規定をv1.1の必須条件として継承しません。

例えば、`6`や`420`を必ず`6.000`や`420.00`と記載する必要はありません。Reader対応範囲とWriter出力精度は、各実装仕様書で別途記録します。特定アプリの固定出力精度はv1.1共通規則ではありません。

## 5. 互換性

### 5.1 v1.1実装でのv1.0入力

`houseRadius` が存在しないJSONはv1.0として扱い、次と同等の座標系として解釈します。

```json
"houseRadius":{"value":1.829,"unit":"m"}
```

これにより、v1.1対応アプリケーションはv1.0 JSONを変更せずに読み込めます。

### 5.2 v1.0実装でのv1.1入力

v1.0だけを認識する既存実装でも、未知の `houseRadius` を無視する場合は、v1.1 JSONの構造自体を読み込める可能性があります。これは構造上の互換性に限られます。

数値的な座標スケールがv1.0の基準（半径1.829）と異なる場合、v1.0実装は構造を解析するだけでは座標を正しく解釈できません。unitラベルの違いだけで数値スケールの互換性が決まるわけではありません。

### 5.3 2種類の互換性

| Compatibility | 日本語での説明 |
| --- | --- |
| 構造上の互換性 | JSONとして解析でき、既知のフィールドを読み取れること。 |
| 座標の意味上の互換性 | 座標のスケールと単位を正しく解釈できること。 |

構造上の互換性があっても、座標の意味上の互換性があるとは限りません。

## 7. 実装上の推奨事項

次の項目は相互運用性を高めるための推奨事項であり、フォーマットの構造上の必須仕様を追加するものではありません。

- `houseRadius` の有無によってv1.0／v1.1を判別します。
- v1.1 Readerは `houseRadius` がない場合に `1.829 m` として解釈します。
- 空白、インデント、改行を互換性判定に使用しません。
- 未知フィールドを無視するv1.0 Readerでも、数値的な半径スケールが1.829と異なる場合は、座標の意味上の互換性を前提にしません。
- v1.1では第4章の半径比・推奨分解能を参照し、未知ラベルだけを理由とした有効データの拒否を避けることを推奨します。

## 8. この仕様で定めない事項

この文書は、v1.0またはv1.1として確定していない要件を追加しません。特に、JSON内部のversionフィールドや、`houseRadius` 以外の構造変更は導入しません。

本仕様は、有効なJSONデータが何を意味するかを中心に定義します。相互運用のために明示した場合を除き、不正入力に対する具体的な回復・拒否動作は実装依存です。ある実装が不正入力を受理・回復しても、その入力が本仕様上有効になるわけではありません。

本仕様で定義していない追加プロパティが存在するだけで、その文書が不正になるわけではありません。本仕様は、それらのプロパティの意味やReaderの処理方法を規定しません。
