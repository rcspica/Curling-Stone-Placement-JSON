# Mobile Curling Editor v1.3.0 実装仕様書

[English](MCE_v1.3.0.md)

日本語版は公式翻訳です。英語版を本実装仕様書の正本とします。一般フォーマット仕様とMCEの対応範囲を区別します。

本書は公開されたMobile Curling Editor v1.3.0を対象とします。

- Android Build 39
- iOS Build 18

## 1. フォーマット仕様とMCEの対応範囲

フォーマットそのものの一次資料は [JSON Text Format v1.1 一般仕様書](../spec/JSON_Text_Format_v1.1.ja.md) です。一般交換仕様と、MCE固有の入力検証・配置制限は別のものです。

一般仕様書では、`houseRadius.value`は12-foot circleの半径を表す有限の正の数で、座標系全体のスケール基準です。`unit`は任意の非空文字列であり、`m`／`ft`／`px`は限定列挙ではなく推奨表記です。

一般的な正規化は`scaleFactor = R_target / R_input`で行うことが可能で、unitラベルの意味を理解することは必須ではありません。未知unitだけを理由に有効データを拒否しないことは一般Readerへの推奨であり、MCE v1.3.0で実装済みの規則ではありません。

v1.1の推奨精度は、半径1.829 m基準で実寸換算約1 mmまたはそれより細かい座標分解能です。目安は`houseRadius.value / 1829`ですが、厳密な丸め規則ではなく、unit別小数桁数や固定有効数字を共通仕様では要求しません。

**MCE v1.3.0はJSON format v1.1への部分対応です。** `houseRadius`なしをv1.0、ありをv1.1として扱います。フォーマットが許容する任意スケールや`px`単位の全域には対応していません。

| 入力 | MCE v1.3.0での扱い |
|---|---|
| `houseRadius`なし | v1.0のメートル座標として受理（標準1.829 m相当） |
| `{"value":1.829,"unit":"m"}` | 座標係数1で受理 |
| `{"value":6,"unit":"ft"}` | 全座標に0.3048を掛けてメートルへ変換 |
| `px`、非標準m／ft、未知unit、解釈不能なhouseRadius | JSON全体拒否 |

半径の比較許容差は`0.0001`で、指定unitのvalueに対して適用します。標準値と異なるスケールへ任意に合わせ直す処理ではありません。`6 ft`ではhouseCenterと各positionの両方を換算します。6 ftを1.829 mへ強制的に一致させる倍率ではなく、固定の0.3048を使います。一般仕様書の`1.829 / 6`（約0.3048333）とは異なり、Readerを半径比による任意スケール正規化へ一般化してはいません。

例えば`{"value":300,"unit":"px"}`や`{"value":100,"unit":"game-unit"}`は一般仕様として有効な座標系ですが、MCE v1.3.0ではSet時に全体拒否します。**JSON v1.1として有効であることと、MCE v1.3.0 Readerが対応していることは同義ではありません。** この差は部分対応の範囲を表すもので、この実装仕様書は対応範囲を拡張するものではありません。

## 2. Setの共通経路と全体拒否

通常Setと2D Code Generateは、同じ検証・適用経路を使います。

```text
JSON解析・全体検証
→ Stone基本検証・座標正規化・完全重複除去
→ 内部座標変換・境界Snap・Playable判定・配置候補確定
→ 現在盤面Clear
→ 配置
→ 履歴／Autosave
→ MCE標準JSON再生成・ボタン更新
```

次の場合は盤面を変更する前にJSON全体を拒否します。

- 入力文字列がJSONとして不正な場合など、JSON解析に失敗する。
- JSON解析は成功するが、トップレベルのJSON値がオブジェクトでない。
- 必須の`metadata`、`positiveDirection`、`houseCenter`、`stones`が欠落。
- positiveDirectionが文字列でない、または許容4方向以外。
- houseCenterがオブジェクトでない、x／yが有限なJSON数値でない。
- stonesが配列でない。
- houseRadiusが存在するが不正、または対応外スケール。
- 基本検証を通過したStoneが同色で8個を超える。
- 同一オブジェクト内の同名プロパティ重複。階層・既知／未知キーを問わず拒否する。

全体拒否では盤面、履歴、Autosave、JSON欄を更新しません。metadataは存在だけを確認し、値・型による生成元制限はしません。未知のプロパティは配置処理に使用せず、存在するだけでは拒否しません。ただし、同名プロパティ重複の検査は適用されます。

## 3. Stone検証と個別スキップ

Stoneは配列順に処理し、入力numberで並べ替えません。次はそのStoneだけをスキップします。

- Stoneがオブジェクトでない、必要フィールドが欠落。
- colorが文字列`red`／`yellow`以外。
- position.x／yが有限なJSON数値でない。
- numberが数値として整数でない、または1〜16の範囲外。
- 正規化結果が非有限、float表現範囲外。
- 正規化後の座標が先行Stoneと完全一致。
- 内部座標変換・境界補正後もPlayable Sheet外。
- 対応する未使用Stoneオブジェクトが存在しない。

数値文字列は数値として扱いません。numberの`1.0`のような整数値は有効です。入力番号は受入範囲内の整数値かを検証し、その番号をStoneへ直接表示しません。Readerは入力番号の一意性や距離順との一致を検査しません。そのため、他の条件を満たす番号重複レコードも適用でき、Set成功後に距離順の一意な番号を再生成します。これは不正入力に対する実装固有の処理であり、番号重複が一般仕様上有効であることを意味しません。

**同色数はcolor／position／numberの基本検証直後に数えます。** 重複除去やPlayable判定より前なので、その後に重複・範囲外としてスキップされるレコードも同色上限のカウントには含まれます。不正な基本レコードは数えません。各色最大8個から全体最大16個が決まり、別の「17個以上」条件は設けていません。全体拒否は、一般仕様の同色上限を超える入力に対するMCE固有の処理であり、一般仕様がこの回復動作を要求するものではありません。

重複判定はメートル化・原点補正・方向正規化後のdoubleのx／y組に対する完全一致です。色には依存せず、後のレコードを除外します。配置用の数値表現への変換や境界補正の後に、近接・一致を新たに重複検査する仕様ではありません。

空配列は正常です。全Stoneが個別スキップされても、全体検証が正常なら空盤面へのSet成功となります。

## 4. 座標正規化

unit換算後、`position - houseCenter`で原点化し、次の符号変換でMCE標準のLeftDownへ揃えます。

| 入力方向 | 原点化後の(x, y)に対する変換 |
|---|---|
| LeftDown | (x, y) |
| RightDown | (-x, y) |
| LeftUp | (x, -y) |
| RightUp | (-x, -y) |

houseCenterは0,0である必要はなく、極端な有限値だけを理由に全体拒否しません。正規化結果の異常・範囲外はStone単位で扱います。

## 5. 出力と再採番

Generate／Set成功後の出力は、シート上のStoneを現在のHouse Centerからの距離順に並べ、色をまたいで1〜Nを再採番したJSONです。出力番号は重複せず、同距離のストーンについて固定した同順位解消順は定めません。固定値とストーン1個の例は次のとおりです。

```json
{ "metadata": "MobileCurlingEditor",
  "positiveDirection": "LeftDown",
  "houseCenter": {"x": 0, "y": 0},
  "houseRadius": {"value": 1.829, "unit": "m"},
  "stones": [
{"color":"red","position":{"x":0.315,"y":-0.428},"number":1}
]}
```

座標は小数3桁で出力します。これは**MCE v1.3.0 Writer固有の出力規則**であり、JSON v1.1共通の桁数・丸め規則ではありません。トップレベルの2行目以降に2スペース、Stoneは1個1行、カンマは行末です。Stoneを含む場合、閉じる`]}`は独立した最終行です。**空盤面の専用生成処理は最終行が`  "stones": []}`です。** 表示上の整形はJSONの互換性条件ではありません。

Set成功後のJSON欄は入力原文ではなく、結果盤面を表すMCE標準JSONに置き換わります。

## 6. JSON境界処理

MCEはJSONの出力・適用時に、シート境界付近の小さな丸め差を補正します。

- Writerは座標を小数3桁へ丸める前に、JSONのYをHouse Top／House Bottomで共通に合法となる範囲へ収めます。この境界補正ではXも盤面上の実座標自体も変更しません。
- Setでは、X／Yが現在のシート境界をわずかに超えた場合、境界上へ戻してからプレイ可能範囲を判定します。JSON往復時の座標丸めに伴う境界超過を吸収するための処理です。
- 補正後もプレイ可能範囲外にあるストーンは個別にスキップします。この補正はプレイ可能範囲を広げず、任意の範囲外座標を受理するものではありません。

これらはMCEのReader／Writer固有の動作で、一般フォーマットの要件ではありません。境界補正と丸めにより、出力座標が盤面上の座標を厳密に保持するとは限りません。

## 7. JSON Save／Load

JSON欄は編集可能な複数行のテキスト欄です。起動時は空盤面JSONを設定します。Loadは欄への文字列設定のみで、自動Setはしません。対応外スケールの文書も欄へLoadできますが、SetまたはGenerate内Setで全体拒否されます。

初期ファイル名は`<SaveFilenamePrefix>yyyyMMdd_HHmmss.json`です。`<SaveFilenamePrefix>`はユーザーが設定できる文字列で、この版では最大6文字とし、設定した値はアプリに保持されます。MCEは生成した名前を保存ピッカーの初期ファイル名として渡し、最終的なファイル名を固定しません。ユーザーは保存前にピッカー上で、ピッカーと保存先のファイル名規則の範囲内で任意の名前へ変更できます。

実機では、この生成名で一時ファイルを作りNative File PickerでExportし、Loadも同プラグインを使います。JSON Loadで`content://`が返された場合は読み込みを中止します。Editorでは生成名を保存ダイアログへ直接渡し、`SaveData`を初期フォルダとするファイルダイアログを使います。

## 8. 2D Codeとの関係

Generateは通常Setと同じ経路で入力を検証・適用し、成功後のMCE標準JSONをQRに格納します。失敗時は新しいPreviewを表示しません。成功時は履歴・Autosave・再採番・JSON再生成も行います。入力原文をそのままQRに保持する機能ではありません。

QRはZXing.NetのQR_CODE、UTF-8、Margin 4を使用します。これはMCEの搬送方法であり、JSON Text Formatの構造要件を追加しません。

画像Read／カメラScanは読み取った文字列をJSON欄へ設定するだけです。JSON検証・Set・盤面変更は自動実行しません。ReadのキャンセルはJSON欄を置き換えません。

## 9. 内部Autosaveと対象外事項

内部Autosave／Restoreは外部JSON Setとは別形式・別経路です。Autosaveは外部Writerの小数3桁整形・共通Y範囲への補正を使用せず、Restoreは外部Setの検証や境界補正を通しません。

任意の有限な正の半径比による入力正規化、pxや未知unitの受理、任意スケールの書き出しはv1.3.0の実装済み機能に含めません。将来版の実装時期は本書で約束しません。
